上线之前，先把“行不行”说清楚

客服 Agent 的内部评测

生产级评测不是一套打分脚本，而是一条从代码断言到人工校准、从单轮对话到最终业务状态、从离线黄金集到线上影子的证据链。下面这份笔记把公开可查的一线做法、学术基准和中文社区实践，整理成一套能直接落地的选型与施工手册。

结果态优先 分层打分器 多轮仿真 Playwright E2E 成本级联 统计门禁
01

评结果，不评台词。先看订单、工单、退款单的最终状态，再看对话说得好不好。

02

代码能判的，绝不交给模型。格式、权限、金额、状态机，先写成确定性断言。

03

一个 judge 只测一件事。能二分类就不要 1–10 分，rubric 写清边界样例。

04

评测集是资产。来自真实失败，按切片版本化，合成数据只做补充。

05

离线分要能对上线上数。不做镜像校准，高分只是自嗨。

00 · 先定问题

先分清三类评测，别用一把尺子量所有事

很多团队一上来就建“评测集”，最后发现分数涨了，线上没变。原因通常不是方法不够多，而是把三种目的完全不同的评测混在了一起。先把决策类型分开，尺子才不会互相打架。

类型回答的问题允许的分数用在哪典型节奏
能力评测 Capability这个模型 / 方案的上限在哪？低分正常，用于比较选基座模型、换架构、评估新工具季度 / 大版本
回归评测 Regression这次改动有没有弄坏已知能力？必须接近 100%，低于阈值拦截Prompt、知识库、工具、模型升级每次提交 / 每日
线上评测 Monitoring真实流量里正在发生什么？看趋势、切片、漂移发布后、灰度、持续运营实时 / 每小时

三者的数据集、容错和成本结构都不一样。能力评测可以用“没见过的难题”探上限；回归评测必须用“已经修过的题”守下限；线上评测则要接受没有标准答案，只能用参考无关的 judge、用户信号和业务结果做代理。

一个容易犯的错

拿回归集去选模型。回归集是你反复优化过的题，模型在上面高分不代表能力强，只代表它“背过答案”。选模型要用独立的 held-out 能力集；回归集只负责防止退化。

另一个常见混淆是“内部 eval”和“上线后监控”。前者是发布前的证据，后者是发布后的雷达。真正生产级的做法，是让两者共享同一套 rubric 和同一套切片定义，这样离线涨 3 分，线上应该能看到对应的方向性变化；如果长期对不上，先怀疑评测，不要怀疑线上。

01 · 评测粒度

客服 Agent 的失败，多数不在最后一句话

一个典型事故：用户说“把收货地址改到公司”，Agent 回复“已经帮您改好了”，语气、格式、礼貌都无可挑剔。但它没有调用改地址工具，或者拿错了订单号，或者改了别人的订单。只看最后一句回复，这个 case 是满分的。

所以评测必须落到四个粒度上。越往右，越接近业务真相，也越难自动化、越贵。

为什么结果态优先

τ-bench 的核心设计就是把评分锚定在数据库的最终状态和必须完成的动作上，而不是让 judge 读一段对话然后打分。Anthropic 在评测方法论里也把 outcome（环境最终状态）和 transcript（对话记录）明确分开，并建议优先验证 outcome。对客服来说，这意味着：

  • 退款任务看退款单是否创建、金额、币种、归属订单；
  • 改地址看订单表的新地址、生效时间、是否触发风控；
  • 转人工看工单是否创建、是否带上下文、是否重复建单；
  • 查询类任务看返回字段是否与 mock 数据一致，而不是看它“说得像不像”。

对话文本仍然是重要的，但它更适合回答“体验好不好”，而不是“事情办成没有”。把两者混成一个 1–10 分，是评测失真的常见起点。

02 · 指标

指标树：结果、过程、体验、安全，外加护栏

客服 Agent 的指标不能只有一个“解决率”。单指标一定会被优化坏：只追求转人工率下降，Agent 就会该转不转；只追求满意度，Agent 就会过度承诺。下面这棵树把“好不好”拆成四层，并要求每层至少有一个护栏指标。

层核心指标怎么测护栏 / 反指标
结果 任务完成率、自助解决率（SSR）、一次解决率（FCR）、重复联系率、正确转人工率、错误转人工率、客诉率、tNPS / CSAT 结果态断言 + 工单/订单数据 + 线上对照 不能只看 containment；要拆“真解决”和“被劝退”
过程 工具选择准确率、参数准确率、调用顺序正确率、确认义务履行率、策略遵循率、幻觉率、检索命中率 轨迹匹配 + mock 工具 + 规则/judge 工具调用次数、无用检索、重复提问次数
体验 语气/共情、澄清质量、简洁度、首响延迟、端到端延迟、打断恢复 LLM judge（校准后）+ 人工抽检 + 埋点 过度礼貌/冗长、模板化、机械重复
安全 越权写操作、PII 泄露、prompt injection 成功率、越界承诺、过度拒答率 红队 + 规则 + 100% 关键路径 judge 拒答率本身是双刃剑，必须同时测误拒
转人工率不是越低越好

要拆成两个数：正确转人工（该转的转了）和错误转人工（能办却推给人）。只看总量，会把“该转不转”伪装成进步。公开实践里常见的健康目标是：正确转人工率上升、错误转人工率下降、重复联系率下降，三者同时看。

公开分享里有一套可以直接借用的阈值样例（Zepto 与 Databricks 的客服栈分享）：意图识别准确率 ≥ 0.93、政策合规 ≥ 0.98、工具选择准确率 ≥ 0.95、语气/共情 ≥ 4.0（5 分制）、p50 延迟 ≤ 1.2s、单次交互成本 ≤ $0.15，并把这些拆成 4 个支柱、11 道门禁。这不是行业标准，而是一个“把软指标写成硬阈值”的示范：每个阈值都要有对应的评测器和切片，否则只是墙上的数字。

中文实践里还有一组更贴近业务的五指标（融 PM）：解决率、幻觉率、转人工率、首轮满意度、业务转化率。其中首轮满意度用点赞/点踩比，20:1 算及格、50:1 算优秀；幻觉率要求无限接近零；转人工率长期应稳定下降，如果超过 50%，说明 AI 只是“智能转接按钮”。这些数字来自公开文章，适合做起步参照，不适合直接当验收线。

03 · 方法库

八种方法，按“成本从低到高”排

生产级评测不是选一种方法，而是搭一条级联：便宜的、确定性的先跑，只有不确定的样本才升级到更贵的判断。下面每张卡都标了成本档和它真正擅长的事。

A. 代码断言与规则

成本 极低
测什么
JSON schema、必填字段、格式、权限、状态机、金额、引用来源、PII 正则、工具调用次数上限。
什么时候用
所有 Agent 的第一层。能写成代码的绝不交给模型；它免费、确定、不会漂移。
坑
按措辞写死规则，会把“正确但表达不同”判错；规则本身也要版本化。

B. 轨迹 / 工具调用断言

成本 低
测什么
工具选没选对、参数对不对、顺序对不对、有没有多调/漏调、写操作前有没有确认。
什么时候用
交易型、工单型 Agent 的必测项。LangChain 的 agentevals 提供 strict / unordered / subset / superset 四种匹配模式，参数还可以按工具自定义比较器。
坑
不要永远用 strict：合理的变体很多。检索类用 unordered，写操作类用 strict 或 subset，并单独校验参数。

C. 小模型 / 蒸馏分类器

成本 低
测什么
意图、情绪、是否越权、是否拒答、政策类别。输出是标签，不是小作文。
什么时候用
高频、低延迟、需要全量跑的信号。公开的蒸馏 judge 与前沿 judge 一致率约 88–92%，成本可降一个数量级（厂商口径）。
坑
需要标注数据；分布漂移后要重训；不要拿它判它没见过的长尾。

D. LLM-as-judge

成本 中
测什么
语义正确、政策解释、共情、澄清质量、多轮目标是否达成——所有无法代码化的软指标。
什么时候用
第二层和第三层。先用小样本校准，再放大；关键 rubric 可以 100% 采样。
坑
位置偏差、长度偏差、自我偏好、rubric 含糊、成本失控。详见下一节。

E. 用户模拟器 / 多轮仿真

成本 中–高
测什么
多轮目标、追问、改主意、不配合、情绪升级、权限受限下的协作。
什么时候用
上线前压测、版本对比、长尾场景。τ-bench、Snowglobe、DeepEval 的 Conversation Simulator 都是这个路子。
坑
模拟用户太配合会系统性高估；对话会变得比真人长；仿真失真需要单独监控。

F. 人工标注 / 专家校准

成本 高
测什么
金标准、judge 校准、争议仲裁、高风险切片的最终裁决。
什么时候用
建 30–300 条 gold set；每周/每月抽检；judge 换模型或换 rubric 时重新校准。
坑
先算标注者一致性：专家自己都吵不出结果，说明 rubric 坏了，不是 judge 坏了。

G. 红队 / 对抗评测

成本 中–高
测什么
prompt injection、越权、诱导承诺、社会工程、过度拒答。
什么时候用
发布前必跑；高风险业务持续跑。通用 jailbreak 不够，要用 policy-aware 的多轮施压。
坑
只测“有没有被攻破”，不测“有没有误伤正常用户”。过度拒答是沉默的成本。

H. Playwright / UI 端到端

成本 中
测什么
真实页面上的聊天窗、富卡片、按钮、转人工、支付/退款页，以及后端副作用。
什么时候用
少量高价值路径，每次发布跑 smoke；浏览器/GUI Agent 用它做任务环境。
坑
不稳定、慢、只测 UI 不测语义；必须和 judge/结果态断言组合。详见第 07 节。
选择顺序

先问“这件事能不能用代码判”。能，就写断言；不能，再问“能不能用一个小分类器判”；还不能，才上 LLM judge；judge 也拿不准的，送人工。这个顺序本身就是成本控制策略。

04 · 模型裁判

LLM-as-judge：能用的前提是被校准过

LLM judge 是过去两年客服评测里最被滥用的一环。它能很便宜地给出一个“看起来合理”的分数，但未经校准的分数和随机数区别不大。生产级用法有五个硬要求。

1. 一个 judge 只测一个维度

不要让一个 prompt 同时打“准确、相关、安全、简洁”四个分。模型会在维度之间做隐式交换：回答更长、更客气，准确分就被抬高。拆成四个独立 judge，每个只回答一个二分类问题，例如“这条回复是否包含对话或检索上下文之外的事实？”、“这次退款操作前是否获得了用户明确确认？”。

2. 能二分类就不要 1–10 分

人类对“是否违反政策”的一致性，远高于“打几分”。二分类还能直接算 TPR/TNR，方便和人工标签对齐。必须分档时，用有明确边界的标签，例如 fully_supported / partially_supported / unsupported / not_applicable，而不是裸露的 1–5。

3. rubric 要写边界，不是写形容词

“回答要有帮助”不是 rubric。“当用户询问退款政策而知识库中没有该商品类目时，正确行为是说明无法确认并转人工，而不是引用相邻类目的政策”——这才是 rubric。要求 judge 先写理由再给结论（理由在前、结论在后），输出固定 JSON；给 2–4 个包含边界情况的示例。若 judge 的理由比 rubric 还长，通常说明 rubric 没写清。

4. 防偏差靠机制，不靠提示词

位置偏差、长度偏差、自我偏好是稳定存在的。有效的做法是：

  • 换位：A/B 比两次，正反各一次，只有两次一致才算赢；高风险场景跑 3 次取多数。
  • 跨家族：judge 和被测模型不要同厂同系，降低自我偏好。
  • 面板：多个 judge 投票，但注意面板也可能放大长度偏差，需要校准。
  • 长度控制：把长度当协变量，统计时回归掉；或在 rubric 中明确“长度不影响正确性”。
  • 参考锚定：有标准答案时用 reference-based 评分，而不是让 judge 自由发挥。

5. 校准与漂移

标准流程：建 30–300 条覆盖真实分布的 gold set（明确成功、明确失败、边界各占一部分）→ 2–3 名业务专家独立标注 → 先算人际一致性 → 再算 judge 与人的一致性。用 Cohen's κ（>0.6 可接受，>0.8 强）或 Krippendorff's α，不要用原始准确率：一个永远说“通过”的 judge，在大多数样本都通过的数据上也能有 90% 准确率。

还要分正负类看：整体一致 92%，但“不可接受”的样本只识别出 13%，这个 judge 不能用来做门禁。每次换 judge 模型、换 rubric、换业务政策，都要重新校准；线上把 judge 与人工的 κ 当成一个独立监控指标，掉下去就告警。

一致性不等于有效性

公开审计里出现过 κ 0.80、但长度偏差 +0.82 的 judge：它和人类很一致，只是因为它和人类一样偏爱长答案。校准要同时看一致性、偏差探针和分切片表现。

RAG 类客服还要额外拆检索与生成：faithfulness 看回答是否被检索内容支持，context precision / recall 看检索本身有没有找对。只测 faithfulness 会出现“忠实地总结了错误段落”的高分假象；公开案例里就有 faithfulness 0.91、但 context precision 很差的情况。RAGAS 是常用起点，但它在表格、长文档、金融类内容上误判率不低，生产上要配人工抽检和规则校验。

05 · 数据

评测集：从真实失败里来，按切片活下去

评测集的质量决定评测的上限。一个由产品经理拍脑袋写的 50 条 FAQ，永远测不出真实事故。下面是公开实践里反复出现的共识。

来源优先级

  1. 真实生产失败：客诉、转人工、差评、工单回访、人工复核发现的问题。这是金矿。
  2. 真实生产日志：随机抽样，保留长尾、方言、错别字、多问题混合、超长输入。
  3. PRD / 验收标准：业务方本来就要验的场景，适合做正向基线。
  4. 合成数据：只用来补长尾和对抗，建议占比不超过 20%，且必须人工审校。

顺序不能反。合成数据便宜，但它是从模型/文档里反推出来的，容易自带“模型已经会了”的偏差；用它做主力，评测会系统性偏乐观。

配比与规模

中文实践里有两套可直接参考的配比：华为云 AgentArts 建议正向 50% / 边界 20% / 对抗 20% / 安全合规 10%，从 30–50 条起步；腾讯云的一篇实践建议 Basic 40% / Edge 30% / Real 30%。两者共同点是：边界、对抗、真实长尾合计要占到一半左右，不能全是“正常问题”。

规模上，Anthropic 建议从 20–50 条真实失败任务起步；51Testing 的实战建议先 50 条再扩到 200–500 条；腾讯云的一线复盘用 200 条双人标注的 Golden Set，加边缘/对抗各 30 条，并设置自动回滚阈值（完成率低于 85%，或连续两次回归跌超 5 个点）。规模不是越大越好，能覆盖切片、能稳定跑、能被人读完，比一万条跑不动的数据更有价值。

一条 case 应该存什么

只存“用户问题 + 标准答案”是不够的。重放时如果检索结果、Prompt 版本、工具返回变了，分数变化就归因不了。建议至少存这些字段：

{
  "id": "refund-0042",
  "slice": ["退款", "VIP", "中文", "含订单号"],
  "input": "我上周买的坚果礼盒还没发货，能退吗？",
  "context": {
    "order_id": "MASKED-xxx",
    "policy_version": "2026-09-01",
    "retrieved_docs": ["refund-policy#3", "shipping-delay#1"]
  },
  "expected": {
    "outcome": { "refund_created": true, "amount": 129.0 },
    "must_call": ["get_order", "check_refund_policy", "create_refund"],
    "must_confirm": true
  },
  "graders": ["outcome_db", "trajectory_subset", "policy_judge"],
  "source": "prod_badcase_2026-09-18",
  "as_of": "2026-09-01"
}

as_of / policy_version 很关键：客服政策会变，半年前的“正确回答”今天可能是错的。冻结政策版本，才能让回归结果可解释。

切片比总分重要

整体 92 分，可能是“普通咨询 98 分、退款 61 分、老年用户 44 分”平均出来的。评测报告必须按意图、渠道、语言、用户等级、金额档、是否含附件、是否多问题等维度切片；每个切片单独设阈值。公开实践里反复强调“均分掩盖高代价失败”，高金额、高权限、可回滚性差的切片，权重和阈值都应该更严。

防泄漏与防过拟合

  • 评测集不要进 Prompt、few-shot、微调数据；
  • 保留一份不参与日常调优的 held-out 集，只在大版本时打开；
  • 定期轮换一部分题，防止团队把公开集“背下来”；
  • 记录每条 case 的来源和最后验证时间，过期题要复核。

06 · 多轮仿真

用户模拟器：把“真实用户的不配合”提前演出来

单轮评测最大的盲区是：真实用户不会一次把需求说清，也不会一直配合。他们会改主意、会不耐烦、会隐藏关键信息、会在你说“已处理”之后追问“那什么时候到账”。用户模拟器就是为这个盲区设计的。

τ-bench 的范式

Sierra 的 τ-bench 把客服评测拆成四件事：业务政策（agent 必须遵守的规则）、工具集、任务、用户模拟器。模拟用户带着隐藏目标和信息来对话，agent 通过工具改变数据库状态；评分不看对话写得好不好，而看最终状态和必须完成的动作是否满足。核心指标是 pass^k：k 次独立尝试全部成功，而不是至少一次成功。

这个指标对客服特别重要。单次成功率 90% 听起来不错，但连续 5 次全对的概率只有 0.9⁵ ≈ 59%；如果单次是 80%，五次全对只有 33%。对客场景要的是“稳定地对”，不是“偶尔惊艳”。公开数据里 GPT-4o 在 retail 域 pass^1 约 61%，pass^8 降到约 25%，差距就是稳定性。

τ²-bench 与双控环境

τ²-bench 把“用户也能操作”纳入环境：客服让用户重启设备、切换设置，用户真的去做了，状态随之改变。这类任务更接近电信、硬件排障、上门服务预约。公开结果显示，顶级助手在新任务上只有 34–49% 的成功率，而且需要“指导用户操作”时还会再掉约 20 个百分点。如果你的客服要指导用户操作 App/设备，单靠文本评测会高估。

生产级仿真：Nubank 的 Snowglobe

Nubank 公开的案例是目前规模最大的生产验证之一：用 Snowglobe 生成合成客户，配合 mock 工具输出，在不碰生产后端的情况下跑完整 agent 工作流；在 Card Delivery / Card Management 两个高频场景上筛了 16,000+ 段模拟对话。结果是自助解决率提升 8.82 个百分点、p95 延迟下降 25%、开发到上线的迭代速度提升 4.8 倍，模拟分数与线上版本分数在 4 个版本上高度相关。

但同一篇论文的复盘也给了重要警告：模拟对话的中位用户词数是 111，真实只有 19；70% 的模拟记录能被业务专家识别为“假”；版本相关性只有 n=4。仿真能加速决策，但不能替代真实流量验证。

仿真设计清单

  • 每个 persona 有明确目标、隐藏信息、情绪基线和“不配合”策略（砍价、拒绝提供订单号、反复改主意）。
  • 模拟用户能执行环境动作（τ² 式双控），而不只是说话。
  • 模拟器本身也要评测：真实性、前后一致性、多样性、能否持续施压。
  • 保留“沉默用户”“答非所问”“一次发多条消息”“中途离开”等真实行为。
  • 仿真结果和真实抽样做对照，至少每季度校准一次失真程度。
  • 语音场景还要叠加 ASR 错误、口音、噪声、打断、网络抖动；公开分析里语音 agent 的准确率可能只有文本的 30–45%。

    • 07 · Playwright

    Playwright 能测什么，不能测什么

    你之前了解到用 Playwright 做评测，这个方向是对的，但要把边界划清楚：Playwright 是执行层和观测层，不是语义裁判。它能非常可靠地回答“用户点了这个按钮之后，页面和后端发生了什么”；它不能回答“这句话说得对不对、合不合规、有没有共情”。

    它真正擅长的四件事

    1. 真实 UI 路径：聊天窗、富卡片、按钮、表单、转人工弹窗、支付/退款页。很多 agent 在 API 层表现正常，一到真实前端就因流式渲染、消息顺序、组件状态出错。
    2. 后端副作用：不要只断言气泡文本。用 Playwright 触发操作，然后查数据库/API/工单系统，确认订单真的改了、退款单真的建了、没有重复建单。这和 τ-bench 的 outcome 断言是同一个思想。
    3. 浏览器/GUI Agent 的任务环境：WebArena 的 812 个任务、BrowserGym 的统一环境，底层都是 Playwright。它们用 accessibility tree 或 HTML 作为观测，用 click/type/navigate 作为动作，评分看最终页面/数据库状态。你要评“后台操作型 agent”，这是现成的骨架。
    4. 开发期的探索与回归：Playwright MCP 让编码 agent 通过 accessibility tree 驱动真实浏览器，适合复现 bug、生成用例、验证 UI 改动；Argos 这类视觉回归可以补上“像素级变化”的证据。

    它不擅长、也不该独自承担的事

    • 语义质量：幻觉、政策解释、语气、共情、澄清是否到位——这些需要 judge 或人工。
    • 多轮目标达成：Playwright 能看到消息发了、按钮点了，但“用户的问题是否真的解决”要靠会话级断言和结果态。
    • 稳定性：实践反馈里，agent 驱动的浏览器测试 10 次可能有 3–4 次跑偏；时序、选择器、流式渲染、网络抖动都会造成假失败。WAREX 的研究还发现，JS 加载延迟超过约 5 秒时，Playwright 系 agent 的退化明显早于 Selenium 系（后者可容忍到约 30 秒）。
    • 成本：每次跑真实浏览器，比纯文本 judge 慢一个数量级，不适合全量回归。
    推荐的生产组合

    硬断言 + 软判断 + 少量 E2E。用 Playwright 跑 5–10 条最高价值的 smoke（下单、退款、转人工、关键卡片），每次发布必跑；用 API/DB 断言覆盖 50–100 条业务路径，每日跑；用 judge 覆盖语义维度，按采样跑。三层各管一段，不要让 Playwright 去判“回答得好不好”。

    让 Playwright 评测不 flaky 的工程要点

    • 固定 data-testid，不要依赖文案和 CSS 层级；文案会变，agent 的输出更会变。
    • 隔离环境：独立租户、固定 seed、mock 支付/物流/风控；写操作要么沙箱，要么可回滚。
    • 把“基础设施失败”和“agent 行为失败”分开：网络/超时/浏览器崩溃可以重试；agent 的随机性不要用重试掩盖，应该记录 pass^k。
    • 每次失败保留 trace、video、截图、网络 HAR、后端状态快照；没有这些，复现成本会吃掉收益。
    • 分层次：PR 跑 smoke（5–10 条，< 5 分钟）；每日跑 full（50–100 条）；每周跑长尾/跨浏览器。
    • 对客服 UI 做视觉回归有意义；对 LLM 文本做像素比对没有意义，文本要用语义断言。

    还有一个容易忽略的观测面：页面暴露给 agent 的工具。Playwright 新版本支持读取页面注册的 WebMCP 工具列表，可以断言“agent 能看到的工具面板”有没有变化。对客服这种页面内嵌 agent 的场景，工具清单变化往往比 DOM 变化更致命。

    08 · 选型

    • 单轮分类/路由型：重点在意图准确率、拒识、错路由成本；用小分类器 + 混淆矩阵，不需要复杂仿真。

    • Human-in-the-loop Copilot：重点在建议质量与采纳率；离线 judge 要和线上采纳率做相关性验证。

    09 · 成本

    成本级联与统计功效：别把预算烧在已经确定的样本上

    生产评测的成本通常不是“模型贵”，而是“用最贵的方法跑了全量”。级联的思路是：绝大多数样本在便宜层就能确定，只有不确定的才升级。

    成本量级

    公开的厂商测算给了一个量级参考：按每天 100 万次判定，纯 LLM judge 约 $5,000/天，纯分类器约 $100/天，三级级联约 $260/天；三者覆盖的 rubric 相同，级联的 p50 延迟也更低，因为大多数样本在第一层就结束。另一组蒸馏 judge 的数据是与前沿 judge 一致率 88–92%、成本降约 97%。这些是厂商口径，用来做预算量级判断可以，不要当报价。

    真正容易被忽略的成本项：judge 的输入 token（长对话 + 长检索上下文会放大）、重复调用（换位、面板、重试）、人工标注、仿真 token、缓存失效后的重跑。缓存要按 judge 版本 + 语料版本 + rubric 版本做 key，否则会悄悄返回过期结论。

    采样率怎么定

    • 100%：合规、PII、越权写操作、退款/赔付、监管相关。单次失败就不可接受，不能抽样。
    • 10–20%：趋势监控、体验类指标、常规回归。κ 保持在 0.6 以上再用于门禁。
    • 1–5%：用前沿 judge 做漂移检测，和线上蒸馏 judge 对照。
    • 按切片加权：高金额、高权限、老年用户、非中文等小切片，样本少但权重要高，必要时全量。

    样本量与统计

    “跑 50 条，涨了 3 分”通常说明不了任何事。粗略的样本量参照：要检测 50% 附近 ±5% 的比例，需要约 385 个样本；±3% 需要约 1,068 个。零失败也不能证明绝对安全：n 次试验零失败时，95% 置信上界约为 3/n（Rule of Three）。只有 30 条全过，真实失败率上界仍有约 10%。

    数据点少于几百时，不要依赖中心极限定理的正态置信区间；用 bootstrap、Wilson 区间或贝叶斯方法。比较两个版本时，同一套题要用配对检验（McNemar / Wilcoxon），并报告效应量和置信区间；比较多条切片时做多重比较校正（如 Benjamini–Hochberg）。统计显著也不等于业务重要，最终还要看切片和绝对值。

    pass^k 的算术

    客服要的是稳定。单次 95% 的任务，连续 10 次全对只有 0.95¹⁰ ≈ 60%；单次 85%，连续 5 次全对只有 44%。所以回归门禁应该看 pass^k，而不是只看一次通过率。

    10 · 上线

    从离线门禁到线上影子：每一层只补上一层看不到的东西

    内部 eval 的终点不是“跑出一个分数”，而是“有资格进入下一层”。生产级路径通常是五段，每段解决不同的盲区。

    离线门禁

    门禁不要只看总分。建议至少四条：整体完成率、关键切片的完成率、关键安全 rubric 的 100% 通过、以及pass^k 的稳定性。任何一条不达标就拦截。阈值要写进 CI，不要靠人看报告。

    门禁的阈值来自历史基线，不是拍脑袋。先跑两周建立方差，再定“低于基线多少、连续几次”才回滚。公开实践里有“完成率低于 85% 自动回滚，连续两次回归跌超 5 点自动回滚”的做法，可以作为起点。

    生产回放

    回放不是把用户问题再问一遍。要保存当时的检索结果、Prompt 版本、工具返回、用户上下文，否则你无法区分“模型变了”和“世界变了”。回放的价值在于用真实分布压测，尤其是长输入、多问题混合、错别字、方言、附件、重复询问这些人工造不出来的形态。

    影子与金丝雀

    • 影子：候选版本看 100% 或采样的真实流量，但 0% 用户看到它的输出。它能测真实推理和真实上下文，但没有结果信号；写操作必须打桩/沙箱，否则会变成事故。多轮对话在第一个分叉之后会发散，长会话的影子结果只能当方向性参考。
    • 金丝雀：1–5% 真实用户看到候选输出，能拿到真实结果，但有真实风险。回滚条件必须提前写死：护栏触发、rubric 滚动均值下降、p99 延迟、候选独有错误簇。不要用随机 5% 去覆盖幂律分布，要按标签分层（内部 → beta → 企业）。
    • A/B：用于因果判断和业务结果（SSR、CSAT、tNPS、成本）。预注册指标、算 MDE、报告置信区间；不要在每次看数后重复做固定样本检验，会抬高假阳性。

    双轨闭环

    小红书的 QCon 分享把这件事讲得比较完整：离线侧固定数据集、任务回放、版本对比；在线侧生产流量采样、持续评估、问题复核；问题回流、数据集版本管理与持续回归衔接。多粒度上覆盖结果、节点、轨迹和多轮任务；评估器上规则、代码、LLM judge、人工校准分工，并通过共享中间结果和串并行编排适配不同业务标准。

    最关键的工程习惯是指标镜像：每一个用来做发布决策的离线指标，都要记录它对应的线上信号、预期差异、切片覆盖和负责人。离线涨、线上不涨，先查镜像是否成立，而不是直接归因于“线上噪声”。

    评测饱和

    当一套回归集长期 100% 通过，它就不再提供信号，只剩下“没坏”的安慰。Anthropic 把这叫 eval saturation，并举了 SWE-bench Verified 从约 30% 涨到 80% 以上的例子。客服团队应该定期做三件事：加入新的真实失败、提高边界难度、把已经稳定的题降频但不删除。

    11 · 反模式

    十二个最常见的坑

    坑表现修法
    只看最后一句话回复很漂亮，工具没调/调错，订单没改加轨迹断言和结果态断言
    平均分掩盖切片整体 92，退款切片 61按意图/金额/渠道切片，单独设阈值
    judge 没校准分数很稳定，但和人工判断不一致gold set + κ + TPR/TNR + 定期复核
    rubric 太模糊judge 理由比 rubric 还长，边界 case 摇摆写边界样例，二分类，一维一 judge
    评测集泄漏分数高，线上差；一换题就崩隔离 held-out，禁止进 Prompt/微调
    合成数据过量仿真里全过，真实用户一用就露馅合成 ≤20%，人工审校，定期对真实分布
    单指标优化转人工率降了，但该转不转、客诉升了拆正确/错误转人工，加护栏指标
    忽略过度拒答安全分满分，正常用户被反复拒绝红队同时测“该拒”和“不该拒”
    环境不稳定同一版本今天 80、明天 65隔离环境、固定 seed、记录基础设施失败
    把 flaky 当退化Playwright 超时被记成 agent 失败区分 infra failure 与 behavior failure
    评测饱和长期 100%，没人再看定期加新失败、提高难度、轮换题
    离线线上脱节离线涨 5 分，线上纹丝不动指标镜像、共享 rubric、回放验证

    12 · 落地

    六周，从“感觉还行”到有证据链

    不需要一开始就建平台。按下面的顺序，每周产出一个可用的东西，六周后基本具备上线前的内部评测能力。

    周产出关键动作验收
    W1失败分类 + 首批 30–50 条 case读 100 条真实 trace，做 open coding，聚类成失败桶；从最高频/最高代价的桶里出题团队能说出前五大失败模式及占比
    W2确定性断言 + 2–3 个二分类 judge先写格式/权限/状态机断言；再写单维度 judge，人工标 50 条算 κjudge κ ≥ 0.6；断言能在 CI 跑
    W3轨迹与结果态评测mock 工具/后端，断言工具序列、参数、最终状态；接 Playwright smoke 5–10 条能复现至少 3 个真实事故
    W4用户模拟器 + 200–500 条切片集persona/隐藏目标/不配合策略；按意图、金额、渠道切片多轮任务有稳定通过率与 pass^k
    W5CI 门禁 + 回归报告整体/切片阈值、关键安全 100%、回滚规则；报告直接给失败 transcript一次发布能被自动拦截
    W6回放 + 影子/金丝雀方案保存检索/Prompt/工具上下文；定义影子打桩范围、金丝雀分层与回滚条件；建指标镜像表离线指标能对上至少一个线上信号

    团队分工

    • 业务/领域专家：定义什么算成功、写 rubric、标注 gold set、仲裁争议。不要让工程师独自决定“业务上对不对”。
    • 评测工程师：搭 harness、写断言和 judge、做校准与统计、维护 CI 门禁。
    • Agent 工程师：提供可观测的 trace、mock 工具、可回滚的写操作、稳定的测试环境。
    • 平台/数据：数据集版本化、切片管理、线上回流管道、dashboard。

    最小可用清单

  • 有一套版本化的黄金集，至少覆盖正向、边界、对抗、安全四类。
  • 每个用例都有明确的成功判据，优先是结果态，其次才是文本。
  • 至少一层确定性断言在 CI 里跑，失败能拦发布。
  • 至少一个校准过的二分类 judge，κ ≥ 0.6，知道它的 TPR/TNR。
  • 评测报告按切片展示，能看到最差切片，而不是只有总分。
  • 每次线上事故都能在 48 小时内变成一条回归用例。
  • 关键路径有 Playwright smoke，且能区分 infra failure 与 behavior failure。
  • 离线指标和线上指标有一张镜像表，定期核对方向是否一致。
    • 一句话总结

    客服 Agent 的内部评测，本质是用尽量便宜、尽量确定的证据，去逼近真实业务结果。方法可以很多，但顺序很稳定：先结果态，再轨迹，再语义；先代码，再分类器，再 judge，再人工；先离线门禁，再回放，再影子。把这条链修好，比追一个新 benchmark 更有用。
