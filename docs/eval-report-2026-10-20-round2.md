# 三:Bad Case 改进与回归决策单(轮次 2)

## 文档信息

Bad Case 编号:C02(seed-价格-final-price);发现:轮 0 基线;修复轮次:第 2 轮。

## Bad Case 定义

输入"推荐三款咸口零食,帮我算最后要付多少"下:(a) `calculate_price` 被排在 `recommendation-decision` 之前,以未筛选的全量候选(按评分 Top5,合计 271.5 元)计价;(b) 推荐决策另选三款(合计 115.7 元),response-generator 混用两组数字,回复金额(233.92 元)与商品事实矛盾,被 risk-check 拦截 → 用户得不到正确试算。两轮均 FAIL 83,risk 层 0 分。

## 期望行为

### 2.1 用户输入风险识别

"付多少/总价"类表述应识别为价格意图,锁定 query_activities/query_coupons/calculate_price 为必经 Tool。

### 2.2 Agent 最终回复

推荐决策完成后,仅对**已选商品**计价;回复中的小计、活动、券、最终价必须与 `calculate_price` Tool 输出一致;试算假设(各 1 件、不含运费)明示。

### 2.3 回复风控

金额与 Tool 证据一致的回复应通过;编造或混用金额的回复必须拦截(轮 0/1 已验证风控可拦截)。

## 当前实际表现(轮1证据)

trace:`… → query_products → calculate_price(先于决策执行)→ …`;risk.issues 原文:"三款商品各1件应为29.9+39.9+45.9=115.7元,而非271.5元";"最终需付金额233.92元…价格试算存在重大错误"。

## 根因分析

### 4.1 根因候选

1. `lib/engine.ts:77` `needsPrice` 正则未覆盖"付多少"类表述 → priceIntent=false → 价格 Tool 未锁为必经,`calculate_price` 由 Planner 作为动态步骤插入,位置在推荐决策之前;
2. Planner 模型排序错误(排除: Planner 只能从白名单选择,位置由 `buildPlan` 组装逻辑决定,与模型无关);
3. response-generator 金额编造(排除: 其输入 ctx.price 来自位置错误的 calculate_price 输出 271.5,数字有"来源",属上游顺序错误的传导)。

### 4.2 根因结论

- 根因类别:确定性代码缺陷(价格意图识别不全,导致步骤组装次序错误)
- 判断依据:正则匹配测试("算最后要付多少"不命中);priceIntent=false 时 requiredTools 不含价格 Tool;trace 中 calculate_price 输入为 Top5 候选(45.9+29.9+25.9+129.9+39.9=271.5,与错误金额精确吻合)
- 排除的其他可能:模型随机(两轮金额错误完全一致,确定性复现)
- 置信度:**高**

## 改进方案

### 5.1 改动目标

只解决:价格意图识别不全导致 C02 计价顺序错误与金额传导错误。不处理评分器与 Prompt 指引(独立变量)。

### 5.2 改动对象

仅 `lib/engine.ts` 第 77 行 `needsPrice` 正则(单变量,确定性代码)。

### 5.3 改动内容(diff)

```diff

+ function needsPrice(input: string) { return /价格|多少钱|付多少|总价|优惠|券|满减|预算|便宜|划算|别太贵|不太贵|省钱|实惠|性价比/.test(input); }
```

影响面验证(改动后、运行前,离线):覆盖 9 条运行用例 + 23 条代表性种子输入,仅 C02 输入翻转(false→true),零误翻转;`tsc --noEmit` 通过。项目无版本库,本 diff 即代码变更证据;Skill/Planner 配置快照(versions.json)未变。
